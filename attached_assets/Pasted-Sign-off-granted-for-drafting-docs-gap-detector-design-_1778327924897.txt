Sign-off decision

The oracle result is strong enough to support the Gap Detector direction.

The central conclusion is valid:

The v2 FactEvaluator is not failing mainly because its logical validation is weak.
It is failing because the candidate representation is too narrow:
subject_entity -- relationship_type -- target_entity.

The experiment shows that many Nexus failures are not representable as simple graph facts. They are dates, scalar values, lists, aggregations, role-scoped facts, quantities, ranges, materials, responsibility semantics, and retrieval gaps.

That is exactly what a Gap Detector should catalog.

The design doc should split them:

A. Ontology / representation gaps
B. Candidate-generation gaps
C. Retrieval/evidence gaps
D. Runtime/infrastructure gaps

Otherwise the Gap Detector will mix product insight with bugs.

4. Treat timeout as a cancellation bug, not a knowledge gap

Q15 and Q18 are not semantic gap evidence. They are runtime failures.

Use:

This matters because the Gap Detector should describe missing representational or reasoning capabilities, while timeout enforcement belongs to reliability engineering.

Recommended D3 thesis

Use this as the top-line thesis:

The oracle-candidate experiment demonstrates that v2’s FactEvaluator cannot serve as the primary recovery mechanism for Nexus failures because the majority of failures cannot be expressed as Fact(subject_entity, relation_type, target_entity). The next system should introduce a Gap Detector that classifies unanswerable or failed questions into typed representational, retrieval, synthesis, and runtime gaps, then routes each gap to the appropriate remediation path.

2. Why the FactEvaluator fails as a recovery layer

State clearly:

The FactEvaluator expects entity-relation-entity triples.
Nexus failures often require non-triple answer objects.
Therefore, feeding the correct answer to v2 still fails when the correct answer is not representable as a graph fact.

Examples:

date → TemporalCandidate
money/count/rate → ScalarMetricCandidate
range → QuantityRangeCandidate
material composition → SpecMaterialCandidate
list → ListCandidate
sum/comparison → AggregationCandidate / ComparisonCandidate
role scoped to org → ScopedRoleCandidate
ownership responsibility → ResponsibilityCandidate

5. Proposed Gap Detector design

The detector should run before candidate evaluation.

class GapDetector:

    def classify(question, extraction_result, retrieval_trace, evaluator_trace):
        if extraction_result.extractable == false:
            return classify_from_extractor_reason(question, extraction_result.reason)

        if extraction_result.fact_shape_invalid:
            return classify_shape_gap(extraction_result)

        if entity_resolution_failed:
            return classify_entity_resolution_gap(extraction_result)

        if retrieval_trace.expected_evidence_absent:
            return GAP_EVIDENCE_NOT_RETRIEVED

        if evaluator_timeout:
            return INFRA_TIMEOUT_CANCELLATION_FAILURE

        if evaluator_returned_underspecified:
            return classify_underspecified(question, evaluator_trace)

        return GAP_UNKNOWN

The key is that the Gap Detector should not merely say “failed.” It should route to the missing subsystem.

Recommended conclusion

Use this conclusion:

The oracle experiment falsifies the assumption that v2’s FactEvaluator can recover most Nexus failures once given the right answer. Even with oracle inputs, the majority of failures collapse before logical validation because the current candidate model cannot represent the answer shape. The next iteration should not tune confidence or add more FactEvaluator rules. It should introduce a Gap Detector and a typed candidate/evaluator architecture.
