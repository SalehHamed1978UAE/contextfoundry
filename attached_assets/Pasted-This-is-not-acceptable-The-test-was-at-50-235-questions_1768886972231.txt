  Run lifecycle never persisted – we aren’t creating a test_runs row when [Start Test] fires. Everything
    lives in an in-memory object, so as soon as the process restarts there’s no record, which is why Test
    History is empty and the Current Test panel falls back to the default “Finished” state. We have to
    insert a test_runs record immediately (status running, vault/question_set IDs, started_at), update it
    after each stage/question, and only mark it complete when progress hits total. Until that’s done, the
    UI has no source of truth.
  - No heartbeat/checkpoint guard – even the “Option A” status file from the spec isn’t being written.
    Without a heartbeat timestamp we can’t tell whether the runner is alive. When the API sees “no worker
    thread” it just returns the default “running=false” payload, so the frontend renders “Finished” because
    it assumes the last run exited normally. We need to write the checkpoint JSON after each question and
    teach /api/test-runner/status to: (a) load the last checkpoint from disk/DB, (b) inspect a heartbeat to
    decide between RUNNING vs INTERRUPTED, and (c) surface the saved stage/progress. Only then can the UI
    render “Interrupted 50/235 – Resume” truthfully.

  Once we have persistent test_runs rows + checkpoint files + heartbeat detection, adding “Resume” is just
