## Goal

Make ontology DB domain IDs the canonical domain registry and wire document classification metadata into the production extraction path without changing extraction behavior yet.

The classifier must produce three pieces of metadata per document, not just one label:

- `primary_domain` — the principal domain ID (e.g., `aerospace_defense`)
- `secondary_domains` — list of additional domain IDs that legitimately appear in the document (e.g., `["finance", "compliance", "security"]` for a board memo)
- `document_type` — what kind of document this is (e.g., `board_minutes`, `technical_spec`, `policy`, `incident_report`, `annual_report`)

`document_type` is **not** the same as `domain` and must not be collapsed into it. `document_type` is the basis for source-authority decisions (board minutes are authoritative for executive appointments; policies are authoritative for ownership/responsibility). `domain` is the basis for ontology-scope decisions (which entity types and relationships are relevant).

### 0.2 — Produce a mapping table

For every distinct label across all registries, produce a row in a mapping table:

| Source registry | Source label | Canonical ontology domain_id | Notes |
|---|---|---|---|

Where:
- **Source registry** is the file path (e.g., `brain/classifier.py:DOMAIN_DESCRIPTIONS`)
- **Source label** is the label as it appears there (e.g., `it_infrastructure`)
- **Canonical ontology domain_id** is the matching `ontology.types.domain_id` value, or `NEW_DOMAIN` if a new ontology domain needs to be created, or `LEGACY_REMOVE` if the label has no canonical mapping and should be archived
- **Notes** explains the mapping decision (e.g., "underscored in classifier, non-underscored in DB; canonical chosen as DB form")

Paste the mapping table for review **before** making any code changes. Wait for sign-off on the mapping before proceeding to 0.3.
