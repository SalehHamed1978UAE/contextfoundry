# Context Foundry Interface Contract
## Platform Foundation ↔ Brain Boundary Specification

**Version:** 1.0  
**Date:** December 2025  
**Purpose:** Define the exact boundary between Platform Foundation and Context Foundry Brain to prevent architectural coupling

---

## 1. Architecture Principle

The Platform Foundation and Context Foundry Brain are **separate modules** that communicate through a **defined interface contract**. They share nothing except:

1. Interface types (this document)
2. A message queue for async operations
3. A query endpoint for sync operations

**Rule:** If you're writing code that imports from both modules, you're doing it wrong.

---

## 2. Interface Contract

### 2.1 Extraction Interface (Async)

Platform Foundation submits extraction jobs to a queue. Brain workers consume from the queue and write results.

#### Request Schema (Platform → Queue)

```typescript
interface ExtractionRequest {
  // Identifiers
  request_id: string;          // UUID, generated by Platform
  document_id: string;         // UUID, Platform's document record
  tenant_id: string;           // UUID, from authenticated session/API key
  
  // Document details
  file_path: string;           // S3/storage path: /tenants/{tenant_id}/documents/{doc_id}/v{n}/original.pdf
  file_name: string;           // Original filename for context
  mime_type: string;           // e.g., "application/pdf", "application/vnd.openxmlformats-officedocument.wordprocessingml.document"
  file_size_bytes: number;     // For estimation
  
  // Extraction context (optional)
  ontology_hints?: string[];   // e.g., ["fibo:financial", "fhir:clinical"] - suggests which ontologies to prioritize
  extraction_mode?: 'full' | 'incremental';  // Default: 'full'
  
  // Metadata
  submitted_at: string;        // ISO 8601 timestamp
  priority?: 'low' | 'normal' | 'high';  // Default: 'normal'
}
```

#### Result Schema (Brain → Results Table/Queue)

```typescript
interface ExtractionResult {
  // Identifiers (echo back)
  request_id: string;
  document_id: string;
  tenant_id: string;
  
  // Status
  status: 'success' | 'partial' | 'failed';
  
  // Results (if success or partial)
  entities_extracted: number;      // Count of entities created
  relationships_extracted: number; // Count of relationships created
  
  // Cost tracking (CRITICAL for metering)
  tokens_consumed: {
    input_tokens: number;          // Tokens sent to LLM
    output_tokens: number;         // Tokens received from LLM
    total_tokens: number;          // Sum
  };
  
  // Timing
  started_at: string;              // ISO 8601
  completed_at: string;            // ISO 8601
  duration_ms: number;
  
  // Error details (if failed or partial)
  error?: {
    code: string;                  // e.g., "EXTRACTION_FAILED", "UNSUPPORTED_FORMAT", "TOKEN_LIMIT_EXCEEDED"
    message: string;               // Human-readable
    recoverable: boolean;          // Can Platform retry?
  };
  
  // Provenance (for audit)
  extraction_version: string;      // Version of extraction pipeline used
  model_used: string;              // e.g., "claude-3-5-sonnet-20241022"
}
```

#### Queue Configuration

```yaml
extraction_queue:
  name: "context-foundry-extraction-requests"
  type: "postgres_notify" | "redis_stream" | "sqs"  # Implementation choice
  
  message_format: "json"
  max_retries: 3
  retry_delay_seconds: [60, 300, 900]  # Exponential backoff
  visibility_timeout_seconds: 600       # 10 min for long extractions
  dead_letter_queue: "context-foundry-extraction-dlq"

extraction_results:
  name: "context-foundry-extraction-results"
  # Platform polls this OR subscribes via notify
  retention_days: 7
```

### 2.2 Query Interface (Sync)

Platform Foundation calls Brain synchronously for queries. This powers the MCP server.

#### Query Request

```typescript
interface QueryRequest {
  // Identity (always required)
  tenant_id: string;
  
  // Query details
  query_type: 'semantic_search' | 'verify_statement' | 'retrieve_entities' | 'get_schema';
  
  // For semantic_search
  query_text?: string;
  max_results?: number;           // Default: 10
  similarity_threshold?: number;  // Default: 0.7
  
  // For verify_statement
  statement?: string;
  
  // For retrieve_entities
  entity_type?: string;           // e.g., "fibo:FinancialInstrument"
  filters?: Record<string, any>;  // e.g., { "currency": "USD" }
  
  // For get_schema
  ontology_domain?: string;       // e.g., "fibo", "fhir", "dcsa"
  
  // Common options
  include_provenance?: boolean;   // Include source document references
  include_confidence?: boolean;   // Include confidence scores
}
```

#### Query Response

```typescript
interface QueryResponse {
  // Status
  success: boolean;
  
  // Results (polymorphic based on query_type)
  results: QueryResult[];
  total_count: number;
  
  // Cost tracking (CRITICAL for metering)
  tokens_consumed: {
    input_tokens: number;
    output_tokens: number;
    total_tokens: number;
  };
  
  // Timing
  duration_ms: number;
  
  // Error (if !success)
  error?: {
    code: string;
    message: string;
  };
}

// Result types
interface SemanticSearchResult {
  entity_id: string;
  entity_type: string;
  content: Record<string, any>;
  similarity_score: number;
  source_document_id?: string;
  confidence?: number;
}

interface VerifyStatementResult {
  verified: boolean;
  confidence: number;
  supporting_entities: string[];
  contradicting_entities: string[];
  explanation: string;
}

interface RetrieveEntitiesResult {
  entity_id: string;
  entity_type: string;
  content: Record<string, any>;
  created_at: string;
  source_document_id: string;
}

interface GetSchemaResult {
  entity_type: string;
  properties: PropertyDefinition[];
  relationships: RelationshipDefinition[];
}
```

#### HTTP Endpoint

```
POST /api/v1/query
Authorization: Bearer {internal_service_key}
Content-Type: application/json

Request body: QueryRequest
Response body: QueryResponse
```

**Note:** This is an INTERNAL endpoint. Platform Foundation calls it; external clients never hit it directly. They go through MCP.

## 3. Data Ownership

### 3.1 Platform Foundation Owns:

```sql
-- Authentication & Identity
users (id, email, name, role, tenant_id, created_at, status, ...)
sessions (id, user_id, token_hash, expires_at, ...)
api_keys (id, tenant_id, key_hash, scopes, rate_limit, expires_at, ...)

-- Multi-tenancy
tenants (id, name, slug, type, status, settings, ...)
tenant_quotas (tenant_id, extraction_tokens_daily, query_tokens_daily, ...)

-- Document Management
documents (id, tenant_id, folder_id, name, status, current_version, ...)
document_versions (id, document_id, version_number, storage_path, ...)
folders (id, tenant_id, parent_id, name, path, ...)
tags (id, tenant_id, name, ...)
document_tags (document_id, tag_id)

-- Usage Metering
usage_events (id, tenant_id, event_type, tokens_consumed, timestamp, ...)
usage_snapshots (tenant_id, snapshot_date, extraction_tokens, query_tokens, ...)
```

### 3.2 Brain Owns:

```sql
-- Knowledge Graph
entities (id, tenant_id, entity_type, content, embedding, source_document_id, ...)
relationships (id, tenant_id, from_entity_id, to_entity_id, relationship_type, ...)

-- Ontology
entity_types (id, domain, name, schema, ...)
relationship_types (id, domain, name, from_type, to_type, ...)
ontology_versions (id, domain, version, published_at, ...)

-- Extraction State (internal to Brain)
extraction_jobs (id, request_id, status, worker_id, ...)
extraction_logs (id, job_id, level, message, timestamp, ...)
```

### 3.3 Shared Column: tenant_id

Both modules use `tenant_id` on relevant tables. Platform Foundation is the **source of truth** for tenant existence and validation. Brain trusts the `tenant_id` passed in requests.

```
Platform: authenticates user/API key → extracts tenant_id
Platform: passes tenant_id to Brain
Brain: uses tenant_id on all records, never validates it
Brain: returns data scoped to that tenant_id
```

---

## 4. What Each Side MUST NOT Do

### Platform Foundation MUST NOT:

- Know how extraction works internally
- Access Brain's entity/relationship tables directly
- Make assumptions about ontology structure
- Retry extraction without Brain confirming `recoverable: true`
- Cache query results beyond a single request (Brain manages caching)

### Brain MUST NOT:

- Validate tenant_id (trusts Platform)
- Know about users, sessions, API keys
- Access Platform's document/folder tables directly
- Enforce quotas (reports consumption; Platform enforces)
- Know about file upload, status tracking, versioning

### Phase 1: Extraction Flow (Week 1)

**Platform Foundation work:**
1. Document upload writes to `documents` table with `status = 'uploaded'`
2. After upload complete, write `ExtractionRequest` to queue, set `status = 'queued'`
3. Poll/subscribe to results, update `status` and log `usage_events`

**Brain work:**
1. Modify extraction pipeline to accept `ExtractionRequest` from queue
2. Add `tenant_id` to all entity/relationship records
3. Return `ExtractionResult` with accurate `tokens_consumed`
4. Write result to results table/queue

**Integration Tests:**

```typescript
// test/integration/extraction-flow.test.ts
describe('Extraction Flow', () => {
  const testTenantId = 'test-tenant-001';
  const testDocId = 'test-doc-001';
  
  beforeAll(async () => {
    // Setup: create test tenant, upload test document to storage
  });
  
  it('Platform submits extraction request to queue', async () => {
    const request = createExtractionRequest(testTenantId, testDocId);
    await platform.submitExtraction(request);

    expect(queuedMessage.tenant_id).toBe(testTenantId);
    expect(queuedMessage.document_id).toBe(testDocId);
  });
  
  it('Brain consumes request and produces result', async () => {
    // Submit request
    const request = createExtractionRequest(testTenantId, testDocId);
    await queue.push(request);
    
    // Wait for Brain to process (with timeout)
    const result = await waitForResult(request.request_id, { timeout: 60000 });
    
    expect(result.status).toBe('success');
    expect(result.tenant_id).toBe(testTenantId);
    expect(result.tokens_consumed.total_tokens).toBeGreaterThan(0);
    expect(result.entities_extracted).toBeGreaterThan(0);
  });
  
  it('Platform updates document status from result', async () => {
    const request = createExtractionRequest(testTenantId, testDocId);
    await platform.submitExtraction(request);
    
    // Wait for full flow
    await waitForDocumentStatus(testDocId, 'extracted', { timeout: 120000 });
    
    const doc = await platform.getDocument(testDocId);
    expect(doc.status).toBe('extracted');
  });

    await waitForDocumentStatus(testDocId, 'extracted');

      event_type: 'extraction',

  it('Entities are created with correct tenant_id', async () => {
    const request = createExtractionRequest(testTenantId, testDocId);
    await platform.submitExtraction(request);
```

### Phase 2: Query Flow (Week 2)

**Platform Foundation work:**
1. MCP server implements tools by calling Brain query endpoint
2. Each query logs `usage_events` with `tokens_consumed`
3. Rate limiting applied before calling Brain

**Brain work:**
1. Query endpoint handles all `query_type` values
2. Returns accurate `tokens_consumed` for each query
3. Respects `tenant_id` scoping on all queries

**Integration Tests:**

- [ ] Extraction tokens tracked per tenant per day

## 7. Error Handling Contract

### Extraction Errors (Brain → Platform)

| Error Code | Meaning | Recoverable | Platform Action |
|------------|---------|-------------|-----------------|
| `EXTRACTION_SUCCESS` | All good | N/A | Update status to 'extracted' |
| `EXTRACTION_PARTIAL` | Some entities extracted, some failed | Yes | Update status to 'partial', allow retry |
| `UNSUPPORTED_FORMAT` | File type not supported | No | Update status to 'failed', notify user |
| `FILE_NOT_FOUND` | Storage path invalid | No | Update status to 'failed', log error |
| `EXTRACTION_TIMEOUT` | Took too long | Yes | Retry with higher priority |
| `TOKEN_LIMIT_EXCEEDED` | Single doc too large | No | Update status to 'failed', suggest splitting |
| `MODEL_ERROR` | LLM returned error | Yes | Retry with backoff |
| `INTERNAL_ERROR` | Unexpected failure | Yes | Retry, alert if repeated |

### Query Errors (Brain → Platform)

| Error Code | Meaning | Platform Action |
|------------|---------|-----------------|
| `QUERY_SUCCESS` | All good | Return results to caller |
| `NO_RESULTS` | Query valid but no matches | Return empty results |
| `INVALID_QUERY` | Malformed query | Return 400 to caller |
| `TENANT_NOT_FOUND` | No entities for tenant | Return empty results |
| `MODEL_ERROR` | LLM error during query | Return 503, suggest retry |
| `INTERNAL_ERROR` | Unexpected failure | Return 500, log error |

## 8. Monitoring Points

### Platform Foundation monitors:
- Queue depth (extraction backlog)
- Extraction latency (time from queued to extracted)
- Query latency (time per query)
- Token consumption rate per tenant
- Quota exhaustion events
- Error rates by type

### Brain monitors:
- Worker utilization
- Extraction success rate
- Average entities per document
- Token cost per document
- Model latency
- Embedding generation throughput

### Alert Thresholds:
- Queue depth > 100: Warning
- Queue depth > 500: Critical
- Extraction error rate > 5%: Warning
- Query error rate > 1%: Critical
- Any tenant at 90% quota: Notify tenant admin

## 9. Deployment Constraints

1. **Separate deployments**: Platform and Brain deploy independently
2. **Interface versioning**: If interface changes, both sides coordinate version
3. **Queue compatibility**: Queue format changes require migration plan
4. **Database migrations**: Each side manages own migrations
5. **Rollback safety**: Either side can rollback without breaking the other (queue absorbs difference)
