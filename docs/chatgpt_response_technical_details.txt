TECHNICAL DETAILS FOR AGGREGATION PROBLEM
==========================================

1. STORAGE FORMAT
-----------------

Entities:
- PostgreSQL table with columns: id, name, entity_type, properties (JSONB), confidence, lifecycle_state
- Properties example: {"role": "President", "department": "Digital Solutions"}
- Graph structure: entities connected via relationships table

Relationships:
- PostgreSQL table: id, source_entity_id, target_entity_id, relationship_type, properties (JSONB), confidence
- Example: Boeing (entity) --HAS_REVENUE--> $2.3B (entity)
- Properties can include temporal info: {"period": "annual", "year": "2024"}

Evidence records:
- Links facts to source: fact_id, fact_type (ENTITY/RELATIONSHIP), evidence_text, source_document_id, chunk_id
- Enables provenance tracking but not always populated

Document chunks:
- Vector store with embeddings
- Metadata: document_id, chunk_index, text content

2. LLM USAGE
------------

Current pipeline uses LLMs for:

Extraction:
- GPT-4o-mini extracts entities/relationships from text chunks
- Returns structured JSON with confidence scores
- Ontology-guided prompts specify allowed entity/relationship types

Answer synthesis:
- GPT-4o-mini generates final answer from retrieved entities/relationships/chunks
- Receives pre-fetched context (not iterative retrieval)
- Single-pass synthesis (no multi-turn reasoning yet)

Retrieval:
- OpenAI embeddings for semantic search
- Tree-based graph traversal (BFS from anchor entity)
- Hybrid: Tree retrieval (70%) + semantic search (30%)

No LLM used for:
- Conflict resolution (currently simple scoring formula)
- Aggregation logic (currently naive first-value selection)
- Quality assessment of extractions
